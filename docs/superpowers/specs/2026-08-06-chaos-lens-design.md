# Chaos lens — แบบร่างการออกแบบ

วันที่ 2026-08-06 · lens แรกของ empeo Inspector

---

## 1. ปัญหา

state ที่ไม่ใช่ "ทุกอย่างปกติ" แทบไม่เคยถูกทดสอบ เพราะการจำลองมันแพงเกินไป

วันนี้ถ้าอยากดูว่าหน้ารายชื่อพนักงานแสดงผลยังไงตอนไม่มีข้อมูล ต้องคอมเมนต์โค้ด แก้ service ให้คืน
array ว่าง หรือไปลบข้อมูลในฐานข้อมูลจริง อยากดูตอน API ช้าต้องไปหน่วงทั้งเบราว์เซอร์ อยากดูตอน
API พังต้องแก้ URL ให้ผิด ทุกวิธีต้องแก้โค้ดแล้วจำไว้ว่าต้องแก้กลับ ผลคือไม่มีใครทำ

ผลลัพธ์ที่เห็นได้จากงานที่ค้างอยู่ในเรโปหลัก — `EMPTY_STATE_MIGRATION.md` และ
`NO_BLOCK_SCREEN_PLAN.md` ทั้งสองไฟล์คือรายการของ state ที่หลุดออกไปถึงมือผู้ใช้เพราะไม่มีใคร
ได้เห็นมันตอนพัฒนา

## 2. เป้าหมาย

เปิด state พวกนี้ให้เห็นได้จากสวิตช์เดียวบนแถบเครื่องมือ โดยไม่ต้องแก้โค้ด ไม่ต้อง build ใหม่
และไม่ต้องแตะข้อมูลจริง

**วัดว่าสำเร็จเมื่อ** dev ในทีมใช้ตรวจ empty state หรือพฤติกรรมจอโหลดของงานที่ทำอยู่จริงได้
โดยไม่ต้องถามวิธีใช้

### ไม่ใช่เป้าหมาย

- ไม่ใช่เครื่องมือ mock API — ไม่มีการสร้างข้อมูลปลอมและไม่มีการเขียน fixture ต่อ endpoint
- ไม่ใช่เครื่องมือทดสอบอัตโนมัติ — คนเป็นคนกดและคนเป็นคนดูผล
- ไม่ทำงานบนระบบของลูกค้า ดูข้อ 8

## 3. หลักการ: แปลงของจริง ไม่สร้างของปลอม

request ออกไปตามปกติ ถึงเซิร์ฟเวอร์จริง ได้ข้อมูลจริงกลับมา แล้วเราค่อยแปลงระหว่างทางกลับ
ก่อนส่งต่อให้แอป

ข้อดีคือใช้ได้กับทุก endpoint โดยไม่ต้องรู้จัก endpoint นั้นมาก่อน ไม่ต้องดูแล fixture และข้อมูล
ที่เห็นบนจอยังเป็นของจริงทุกฟิลด์ แค่ถูกทำให้มากขึ้น น้อยลง ยาวขึ้น หรือมาช้าลง

**request ขาออกไม่ถูกแก้ไขเลย** — header, body, token, URL ส่งไปตามเดิมทั้งหมด เครื่องมือแตะ
เฉพาะขากลับ จึงไม่มีทางเขียนข้อมูลผิดลงฐานข้อมูล ยกเว้นโหมดข้อผิดพลาดที่ตัดจบตั้งแต่ต้นทาง
ไม่ยิงออกไปเลย

## 4. จุดที่แทรก

```
Component
   ↓
HttpClient
   ↓
TokenInterceptor          ← incrementLoading / incrementBlockScreen อยู่ที่นี่
   ↓
XMLHttpRequest / fetch    ← แทรกที่นี่
   ↓
api.empeo.com
```

แทรกที่ชั้น XHR และ fetch ใน MAIN world ตอน `document_start` ด้วยเหตุผลสามข้อ

1. **ไม่ต้อง build แอปใหม่** เปิด UAT ที่ deploy อยู่แล้วก็ใช้ได้ทันที ซึ่งเป็นเงื่อนไขสำคัญที่สุด
   ต่อการที่ทีมจะได้ใช้จริง
2. **ครอบ micro-app ด้วย** `ma-*` มี `HttpClient` และ interceptor ของตัวเองอยู่ในบันเดิลของ
   core-web แต่รันใน window เดียวกับเชลล์ การดักที่ชั้นล่างจึงจับได้ทั้งสองฝั่งด้วยโค้ดชุดเดียว
3. **ปล่อยให้ `TokenInterceptor` ทำงานตามปกติ** ตัวนับ loading และคำสั่งเปิดจอ block อยู่ใน
   interceptor ถ้าไปแทรกเหนือมันเราจะกลบพฤติกรรมที่ตั้งใจจะทดสอบพอดี

## 5. สี่โหมด

ทุกโหมดใช้เครื่องยนต์เดียวกันและเลือกได้ทีละโหมด

### 5.1 จำนวนแถว — `0 · 1 · 20 · 100 · 1000`

1. parse response เป็น JSON ถ้า parse ไม่ได้ให้ผ่านไปโดยไม่แตะ
2. เดินหาทุก array ที่สมาชิกเป็น object บันทึก path กับความยาว
3. **รายการหลัก** คือ array ที่ยาวที่สุด ถ้าเท่ากันเลือกอันที่อยู่ตื้นกว่า
4. ถ้า N น้อยกว่าความยาวเดิม ให้ตัด ถ้ามากกว่าให้วนซ้ำ item เดิมจนครบ
5. สำเนาที่วนซ้ำต้องแก้ค่าประจำตัวไม่ให้ชน — คีย์ที่เข้าเกณฑ์ `id` `*Id` `*No` `guid` `key`
   ถ้าเป็นตัวเลขให้บวก index ถ้าเป็นข้อความให้ต่อท้าย `-<index>`
6. ฟิลด์ตัวเลขที่เป็นพี่น้องกันและชื่อเข้าเกณฑ์ `total` `totalCount` `totalRecords` `count`
   `recordCount` ให้ปรับเป็น N ตาม มิฉะนั้น paginator จะเพี้ยน

`0` ให้ empty state · `1000` ให้เห็นว่า virtual scroll กับ sticky header ทำงานจริงไหม

### 5.2 หน่วงเวลา — `1s · 3s · 10s`

ถือ response จริงไว้ตามเวลาที่ตั้งก่อนส่งต่อ ไม่แตะเนื้อข้อมูล

เปิดโปงหลายเรื่องพร้อมกัน — จอ block เต็มหน้าที่ขึ้นทั้งที่เป็นการอ่านข้อมูล, skeleton ที่กระพริบ,
ปุ่มบันทึกที่กดซ้ำได้ระหว่างรอ, และ call ที่ควรยิงขนานกันแต่กลับต่อคิว

### 5.3 ข้อผิดพลาด — `500 · 403 · 404`

ตัดจบตั้งแต่ต้นทาง ไม่ยิงไปหาเซิร์ฟเวอร์ แล้วคืน status ที่เลือกพร้อม body ว่างกลับไป

**ไม่รองรับ 401** เพราะจะไปกระตุ้น `handle401Error()` ใน `TokenInterceptor` เข้าสู่ refresh-token
flow แล้วทำ session พังโดยไม่ได้ผลอะไรกลับมา

### 5.4 ข้อความยาว — `ไทย · EN · ไม่เว้นวรรค` × `×2 · ×5 · ×20`

ต่อท้ายข้อความเดิม ไม่แทนที่ ค่าเดิมยังอ่านออกทำให้รู้ว่าพังที่ฟิลด์ไหน

สามแบบเพราะทำ CSS พังคนละที่ — แบบมีเว้นวรรคทดสอบการยืดกรอบ, แบบไม่เว้นวรรคทดสอบ
`overflow-wrap` ที่ตั้งผิดซึ่งเป็นเคสที่คนลืมมากที่สุด, แบบไทยเพราะไทยไม่มีช่องว่างระหว่างคำ
เบราว์เซอร์จึงตัดบรรทัดคนละแบบกับอังกฤษ

## 6. ฟิลด์ที่ห้ามแตะ

ใช้กับโหมดข้อความยาวเป็นหลัก และกับการแก้ค่าประจำตัวในโหมดจำนวนแถว

**ข้ามตามชื่อคีย์** (ไม่สนตัวพิมพ์ ดูที่คำลงท้าย) — `url` `uri` `src` `href` `path` `link` `token`
`key` `guid` `id` `no` `code` `type` `status` `mime` `hash` `color` `icon` `lang` `locale`
`timezone` `version`

**ข้ามตามหน้าตาของค่า** — ขึ้นต้นด้วย `http://` `https://` `data:` · เป็นวันที่รูปแบบ ISO ·
เป็น GUID · เป็นตัวเลขล้วน · เป็น `SCREAMING_SNAKE_CASE` · สั้นกว่า 3 ตัวอักษร

เหตุผลคือค่าพวกนี้ไม่ใช่ข้อความให้คนอ่าน การยืดมันทำให้แอปพังด้วยเหตุผลที่ไม่มีอยู่จริง ซึ่ง
อันตรายกว่าการไม่มีโหมดนั้นเลย เพราะคนจะเลิกเชื่อผลที่เครื่องมือรายงาน

## 7. เลือกขอบเขต

หน้าเดียวยิง API หลายตัว ถ้าแกล้งทั้งหมดพร้อมกัน dropdown จะว่าง เมนูจะหาย ปุ่มจะหายเพราะ
ไม่มีสิทธิ์ จนดูไม่ออกว่าอันไหนคือสิ่งที่อยากดู

popup จึงแสดง **รายการ request ที่เพิ่งเกิดจริงบนหน้าที่เปิดอยู่** ให้ติ๊กเลือก ไม่ต้องให้ใครพิมพ์ URL

```
แกล้งตรงไหน
  ◉ ทั้งหน้า
  ○ GetEmployeeList     342 แถว
  ○ GetAll (Department)  18 แถว
  ○ GetSetting              —
```

แต่ละแถวบอกจำนวนสมาชิกของ array ที่ยาวที่สุดใน response นั้น ทำให้เห็นทันทีว่าตัวไหนคือตารางหลัก
ตัวไหนคือ dropdown ตัวไหนไม่ใช่รายการเลย และเป็นการเปิดเผยผลการเดา "รายการหลัก" ในข้อ 5.1
ให้เห็นแทนที่จะเดาลับหลัง

ค่าเริ่มต้นคือ **ทั้งหน้า** เพราะตอนกวาดหา empty state ที่ยังไม่ได้ทำทั้งระบบต้องการแบบเหวี่ยงแห
ส่วนช่องพิมพ์ pattern เองเก็บไว้ใต้หัวข้อขั้นสูง

รายการ request เก็บในหน่วยความจำของ content script รีเซ็ตเองเมื่อเปลี่ยนหน้า

### ตัวกรองที่ทำงานเสมอ

ข้าม request ที่ไม่ใช่ API ทุกกรณี — นามสกุล `.js` `.css` `.map` `.svg` `.png` `.jpg` `.woff*`
และ response ที่ไม่ใช่ JSON

**ไม่กรองตาม HTTP method** — empeo ใช้ `POST` และ `PUT` สำหรับการอ่านข้อมูลอยู่จำนวนมาก
ดังที่ `NO_BLOCK_SCREEN_PLAN.md` ในเรโปหลักไล่รายการไว้ ถ้าจำกัดไว้แค่ `GET` จะพลาดการอ่าน
ส่วนใหญ่ของระบบ นอกจากนี้โหมดหน่วงเวลาบนการบันทึกข้อมูลคือวิธีเดียวที่จะเห็นว่าปุ่มบันทึก
ถูกกดซ้ำได้หรือไม่

จำเป็นเพราะตอน `ng serve` แอปโหลด chunk เป็นร้อยก้อน ถ้าโหมดหน่วงเวลาไปถ่วงด้วยแอปจะอืด
จนใช้ไม่ได้แล้วคนจะเข้าใจว่าเครื่องมือพัง

## 8. การกันไม่ให้ไปโผล่บนระบบลูกค้า

**อนุญาตเป็นรายชื่อ ไม่ใช่ห้ามเป็นรายชื่อ**

```
http://localhost/*            (ทุกพอร์ต — 4200, 44399, 3000)
http://127.0.0.1/*
https://portal.dev.empeo.com/*
https://portal.uat.empeo.com/*
```

เพราะ empeo เปิดให้ลูกค้าตั้งโดเมนของตัวเองต่อ tenant ได้ การไล่แบนโดเมน prod ทีละอันจึงรั่ว
เสมอ ส่วน `localhost` ปลอดภัยโดยนิยามเพราะเป็นระบบของลูกค้าไม่ได้

เชลล์ของ venio ยังไม่รวมในรอบนี้

**กันสามชั้น**

1. `host_permissions` ในไฟล์ manifest มีแค่รายชื่อข้างต้น
2. popup ไม่แสดงส่วนควบคุมเมื่อเปิดบนโดเมนอื่น
3. สคริปต์ที่ฉีดเข้าไปตรวจ `location.origin` ของตัวเองซ้ำก่อนติดตั้ง patch โดยไม่เชื่อหน้าจอ

**เห็นตลอดว่าเปิดอยู่** ขอบสีส้มรอบหน้าจอกับแถบสถานะค้างไว้ตลอดเวลาที่ทำงาน พร้อมข้อความ
บอกโหมดและขอบเขตที่เลือก เพื่อไม่ให้ใครเข้าใจผิดว่าสิ่งที่เห็นตรงหน้าเป็นบั๊กจริง

**กฎเก็บใน `chrome.storage.session`** ปิดเบราว์เซอร์แล้วหายเอง ไม่ต้องมีตัวจับเวลาหมดอายุ

## 9. โครงสร้างและการสื่อสาร

```
popup  ──sendMessage──▶  content bridge  ──postMessage──▶  chaos (MAIN world)
       ◀───────────────                  ◀───────────────
       รายการ request                     บันทึก request
```

| ส่วน | โลก | หน้าที่ |
| --- | --- | --- |
| `src/popup/` | extension | UI เลือกโหมดและขอบเขต อ่านรายการ request เขียนกฎลง storage |
| `src/content/bridge.ts` | isolated | ส่งกฎเข้า MAIN world เก็บรายการ request ไว้ในหน่วยความจำ ตอบ popup |
| `src/inject/chaos.ts` | MAIN | patch `XMLHttpRequest` กับ `fetch` ใช้กฎ ส่งบันทึกกลับ |
| `src/shared/transform.ts` | — | ฟังก์ชันแปลง JSON ล้วน ไม่มี side effect ทดสอบได้ตรง ๆ |
| `src/shared/allowlist.ts` | — | รายชื่อโดเมนที่อนุญาต ใช้ร่วมกันทุกส่วน |

ลงทะเบียนสคริปต์ MAIN world ด้วย `chrome.scripting.registerContentScripts` ตอนติดตั้งและตอน
เบราว์เซอร์เริ่มทำงาน กำหนด `runAt: 'document_start'` และ `matches` ตามรายชื่ออนุญาต

**การแข่งกันของเวลา** สคริปต์ MAIN world ติดตั้ง patch ทันทีเสมอ แต่กฎมาถึงทีหลังผ่าน
`postMessage` ทุก request ที่ถูกดักจึงรอ promise ของกฎก่อนตัดสินใจ ในทางปฏิบัติกฎมาถึงภายใน
ไม่กี่มิลลิวินาที ขณะที่ API ตัวแรกของ Angular ยิงหลังจากนั้นหลายร้อยมิลลิวินาที

`postMessage` มองเห็นได้จากหน้าเว็บ ยอมรับได้สำหรับเครื่องมือ dev แต่ต้องตั้งชื่อ type ให้ไม่ชน
และตรวจ `event.source === window` ทุกครั้ง

## 10. การ build และแจกจ่าย

TypeScript รวมด้วย esbuild ออกไปที่ `dist/` แล้ว **commit `dist/` เข้าเรโป**

เพื่อให้เพื่อนในทีม clone แล้ว load unpacked ชี้ที่ `dist/` ได้เลย และอัปเดตด้วย `git pull`
อย่างเดียวโดยไม่ต้อง `npm install` — friction ตรงนี้คือสาเหตุที่เครื่องมือภายในตายบ่อยที่สุด

```
manifest.json
src/{popup,content,inject,shared}/
test/
dist/                                  ← commit
docs/superpowers/specs/
```

คำสั่ง `npm run build` และ `npm run watch` สคริปต์ build คัดลอก `manifest.json` กับไฟล์ของ
popup ไป `dist/` ด้วย

`extension ID` ของ unpacked ผูกกับ path บนเครื่องแต่ละคน ถ้าวันหนึ่งต้องการ ID คงที่ให้ใส่ฟิลด์
`key` ในไฟล์ manifest

## 11. การทดสอบ

ส่วนที่ทดสอบอัตโนมัติได้คือ `transform.ts` ซึ่งเป็นฟังก์ชันล้วน ใช้ `node --test` กับ fixture ที่
คัดลอกรูปร่างมาจาก response จริงของ empeo

ครอบคลุมอย่างน้อย — เลือกรายการหลักถูกเมื่อมีหลาย array · แก้ค่าประจำตัวไม่ให้ชนตอนวนซ้ำ ·
ปรับ `total` ตาม · ไม่ยืดฟิลด์ที่อยู่ในรายการห้ามแตะ · ปล่อยผ่านเมื่อ parse JSON ไม่ได้

ส่วน patch ระดับ XHR ทดสอบด้วยรายการตรวจด้วยมือบน `portal.uat.empeo.com` เพราะต้องพิสูจน์กับ
Angular ตัวจริง

## 12. ความเสี่ยงที่รู้ตัว

**การหน่วง XHR เป็นงานที่ยากที่สุดในสเปกนี้** `responseText` เป็น read-only และหน้าเว็บผูก
handler ของตัวเองไว้ ต้องดักทั้ง `addEventListener` และ setter ของ `onload` กับ
`onreadystatechange` แล้วนิยาม property ใหม่บน instance ก่อนเรียก handler ของหน้าเว็บ
ควรทำเป็นงานสำรวจแยกก่อนเริ่มงานหลัก และถ้าไม่รอดให้ตัดโหมดหน่วงเวลาออกจากรอบแรก
ส่วนฝั่ง `fetch` ง่ายกว่ามากเพราะสร้าง `Response` ใหม่คืนได้ตรง ๆ

**แอปที่ cache ข้อมูลไว้แล้ว** ถ้า service เก็บผลไว้ตั้งแต่รอบแรก การเข้าหน้าเดิมซ้ำจะไม่ยิง API
เครื่องมือจึงไม่มีผล ต้องเขียนกำกับไว้ในแถบสถานะว่ามีผลกับข้อมูลที่โหลดใหม่เท่านั้น และมีปุ่ม
โหลดหน้าใหม่ใน popup

**response ที่ไม่ใช่ JSON** `TokenInterceptor` สั่ง `responseType: 'blob'` สำหรับรูปและไฟล์แนบ
ต้องปล่อยผ่านทั้งหมด

**socket.io และ SSE ไม่ถูกดัก** แชทและการแจ้งเตือนจึงไม่ได้รับผล ถือเป็นข้อจำกัดที่ยอมรับ

## 13. ตัดออกพร้อมเหตุผล

| ตัด | เหตุผล |
| --- | --- |
| ไฮไลต์ข้อความล้นและ tooltip | เป็นการสแกน DOM ไม่ใช่การแปลง response คนละกลไก ย้ายไป lens ตรวจ convention |
| ทำรูปพัง | ยังไม่มีใครขอ |
| ครอบวงเล็บหาคำที่ลืมแปล | ยังไม่มีใครขอ |
| ดัน total ให้เยอะโดยไม่แตะ items | ทับซ้อนกับโหมดจำนวนแถว |
| ค้างไม่ตอบกลับตลอดกาล | การ grep หา `.subscribe(` ที่ไม่มี `takeUntilDestroyed` จับปัญหากลุ่มเดียวกันได้ถูกกว่าและมีอยู่ในกระบวนการ review แล้ว |
| ช้าครั้งแรกเร็วครั้งหลัง | ตีความผลยาก แยกไม่ออกว่าเป็น race หรือ change detection ปกติ |
| สลับ role | สิทธิ์ถูก cache ใน `localStorage` และหลังบ้านยังบังคับตามสิทธิ์จริง ผลจะเปลี่ยนแค่ครึ่งเดียวจนไล่ผี |
| ยืดทุกสตริงโดยไม่กรอง | ทำลาย URL กับวันที่ แอปพังด้วยเหตุผลที่ไม่มีอยู่จริง |
| status 401 | กระตุ้น refresh-token flow จน session พัง |
| status 202 | empeo ตีความเป็น error แต่ยังไม่รู้ว่าเจอบ่อยแค่ไหนในของจริง |
| เชลล์ venio | ขอบเขตแคบไว้ก่อน ค่อยเพิ่มทีหลังได้ |
